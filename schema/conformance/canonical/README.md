# Canonical Form Conformance Pack (`klm-canonical/1`)

Vectors and behavioural checks for the byte form that KLM attestation records
are hashed and signed under (Specification §6.4, v0.3 amendment E1). If two
implementations disagree on these bytes, a correctly signed record looks
tampered with to one of them, so KLM-5 verification depends on it.

## Why this exists (E1)

Up to v0.2.2 the reference signer called its canonicalization "the normative
rule", but the rule was Python's `json.dumps(sort_keys=True,
separators=(",", ":"), ensure_ascii=False)`, and the specification never
defined a canonical form. Python writes an integral float as `1.0`/`0.0`.
JavaScript has no float/integer distinction, so `JSON.stringify` writes `1`/`0`.
Any record with a score of exactly 0 or 1 therefore hashed differently in the
two languages, and nothing had been altered. The two also differ on exponent
layout (`1e-07` vs `1e-7`, `1.2345678901234568e+20` vs `123456789012345680000`),
on `-0.0`, and on the order of object keys that mix astral characters with
BMP characters above U+E000.

The defect was found by an independent TypeScript verifier written by the same
team. It was not found by a third party. Internal Python-only testing could
not have seen it.

## The forms

| id | status | definition |
|---|---|---|
| `klm-canonical/1` | **normative**; used for every new signature | RFC 8785 JSON Canonicalization Scheme (JCS) |
| `klm-canonical/0-pyjson` | **legacy, verify-only** | the v0.2.2 Python rule above, kept byte-for-byte |

`klm-canonical/1`, in short:

- Object keys are sorted by their **UTF-16 code units**. This is not the same
  as code-point order: U+1F600 (`D83D DE00`) sorts *before* U+FB33.
- No insignificant whitespace.
- Strings: only `"` and `\` are escaped, plus the controls U+0000–U+001F. Those
  use `\b \t \n \f \r` where one exists and `\u00xx` (lowercase hex)
  otherwise. Everything else is emitted verbatim as UTF-8, including `/`,
  U+007F and U+2028/2029. Lone surrogates are refused.
- Numbers are written exactly as ECMAScript `Number.prototype.toString` writes
  them: the shortest round-trip digits, with no `.0` on integral values, and
  `-0` becomes `0`. Plain notation is used for 1e-7 < |x| < 1e21. Outside that
  range the form is `d[.ddd]e±n`, e.g. `1e+21` or `1.5e-7`.
  `NaN`/`±Infinity` are refused.
- Integers outside ±(2^53−1) (`Number.MAX_SAFE_INTEGER`, I-JSON) are refused,
  because a JavaScript verifier cannot hold them exactly. Encode such values
  as strings.
- `true`, `false` and `null` are written as literals.

## Dispatch rule

A record, or the envelope that carries it, MAY declare its form in a
top-level string field `canonicalization`.

1. **Signing** always uses `klm-canonical/1` and writes
   `"canonicalization": "klm-canonical/1"` into the envelope.
   `signature.record_hash` is the sha256 of the record's `klm-canonical/1`
   bytes. A record that itself declares a different form is refused.
2. **Verification** branches on the declaration:
   - `klm-canonical/1` → JCS.
   - **absent** → `klm-canonical/0-pyjson`. The result is reported as legacy.
     This is how every pre-v0.3 envelope keeps verifying.
   - any other value, including an unknown id, `null`, `""` or a number → an
     explicit error. The verifier never guesses and never falls back silently.
   - envelope and record both declare, and they disagree → an explicit error.
3. **Hash-chained log** (`attestation_log.py`). Every new entry carries
   `"canonicalization": "klm-canonical/1"` inside its hashed body. Entries
   without the field are pre-v0.3 entries and verify exactly as before. A
   legacy entry that appears *after* a `klm-canonical/1` entry is reported as
   a downgrade.
4. **Disclosure views** (`disclosure.py`). `record_ref` now names the
   `canonicalization` its `record_hash` was computed under. For an envelope
   this is the envelope's form. For a bare record it is the record's own
   declaration, or legacy when the record declares nothing. A bare undeclared
   record does not say how it was signed, so pass the envelope if you have it.

**Why the envelope-level declaration need not be signed.** The signature
covers the canonical bytes. If an attacker changes the declared form, the
verifier re-derives different bytes and the check fails. There is one
exception, when both forms produce identical bytes for this record. In that
case the record parses back to the same JSON value, so no meaning has changed.
Both forms are faithful serialisations: if two records produce the same bytes
under any pair of forms, the two records hold the same JSON value.

## Files

| file | what |
|---|---|
| `vectors.json` | 64 accept cases and 8 reject cases. For each: `input` (a JSON text), `expected` (the canonical string), and `sha256` (over its UTF-8 bytes). **Generated by Node, not typed by hand.** Includes the RFC 8785 §3.2.2/§3.2.3 examples and all Appendix B IEEE-754 bit patterns. |
| `jcs_reference.mjs` | JavaScript reference — a ~12-line `canonicalize()`: `JSON.stringify` for numbers and strings, default `sort()` for keys, plus refusals |
| `gen_vectors.mjs` | regenerates `vectors.json` (`node gen_vectors.mjs`) |
| `legacy-vectors.json` | `klm-canonical/0-pyjson` outputs produced by the **original** v0.2.2 `canonical_bytes` (git `0ec1a97`) |
| `fixtures/legacy-envelope-v0.2.2.json` | an envelope signed by the original v0.2.2 code over a real record that contains `1.0`/`0.0` and non-ASCII text |
| `fixtures/legacy-log-v0.2.2.jsonl` | a two-entry chain written by the original v0.2.2 `attestation_log.py` |
| `run_conformance.py` | the runner (stdlib only) |

The fixtures are signed with a **public** test key,
`sha256("klm-canonical conformance fixture key -- PUBLIC, NOT A SECRET")`.
They prove nothing about who signed them. They only prove the bytes.

## Run

```bash
python3 run_conformance.py
```

The runner checks four things:

1. Python output matches every vector byte-for-byte, and every reject input
   raises.
2. The legacy path is byte-identical to v0.2.2.
3. A live cross-check against the Node reference, **skipped (not failed)**
   when `node` is not on PATH.
4. Behaviour:
   - (a) the E1 record hashes as Node does;
   - (b) the v0.2.2 envelope verifies and is reported as legacy;
   - (c) a sign → verify round trip under `klm-canonical/1` also survives a
     JavaScript `JSON.parse`/`stringify`, which the legacy envelope does not;
   - (d) unknown, malformed and conflicting ids are errors;
   - (e) old log chains verify, new entries declare `klm-canonical/1`, and
     tampering and downgrades are caught;
   - (f) the disclosure `record_ref` matches the signed hash;
   - (g) every shipped example and evidence record still gets its pre-v0.3
     bytes through the undeclared default path.

The runner exits 0 only if every check passes.

**Porting.** In JavaScript, `jcs_reference.mjs` is the whole implementation.
Other languages need the ECMAScript number layout on top of a shortest
round-trip digit generator (Ryū, Grisu or Dragon4). In Python, `repr(float)`
supplies those digits. Run your implementation against `vectors.json`.

## Honest gaps

- **Duplicate keys** in an input JSON text cannot be detected once the text
  has been parsed. Python keeps the last value, and so does JavaScript. JCS
  requires I-JSON input, which has no duplicates, but this pack cannot test
  for it.
- The **out-of-range integer** reject vectors can only be checked by an
  implementation that parses exact integers. A JavaScript parser has already
  rounded the value to a double.
- **Older verifiers.** A verifier from v0.2.2 or earlier ignores the new
  declaration. It still accepts `klm-canonical/1` envelopes whose bytes happen
  to match both forms. For any other record it reports "record_hash mismatch
  — record was altered", which is a false tamper alarm. Upgrade verifiers
  before relying on new envelopes. The envelope schema id is still
  `klm-attestation-envelope/0.1`.
- This pack covers the KLM reference toolchain only. Canonical forms that
  other products use for their own receipts are separate formats.
